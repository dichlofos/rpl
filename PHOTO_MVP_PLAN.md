# План реализации фото-MVP RPL

## Назначение

Документ задаёт рекомендуемую последовательность реализации функциональности,
описанной в [PHOTO_WORKFLOW.md](PHOTO_WORKFLOW.md). Работа разбита на вертикальные
срезы: каждый этап должен завершаться проверяемым результатом, пригодным для
испытания на реальных фотосетах.

Критический путь:

```text
временные точки GPX
→ серверная модель и API
→ каркас LRPL
→ импорт и калибровка
→ дни и фильтрация
→ рабочие копии
→ аннотации
→ упаковка под три ОС
```

## 0. Исследовательский прототип

До разработки серверного интерфейса создать небольшой локальный CLI-прототип:

- прочитать каталог JPEG;
- извлечь EXIF;
- определить камеры и диапазоны времени;
- сопоставить фотографии с одним или несколькими GPX;
- предложить временной сдвиг;
- посчитать perceptual hash;
- сформировать стопки похожих кадров;
- оценить относительную резкость внутри стопки.

Прототип проверить на нескольких существующих наборах:

- одна и несколько камер;
- неправильная таймзона или часы камеры;
- фотографии без GPS;
- разрывы записи трека;
- серии похожих кадров;
- обработанные копии одного изображения.

Результат этапа — зафиксированные алгоритмы, настраиваемые пороги и набор
воспроизводимых тестовых примеров. Это ещё не пользовательское приложение.

## 1. Временная геометрия треков

Сейчас RPL сохраняет координаты трека и общие `started_at`/`finished_at`, но не
сохраняет временные метки отдельных точек в производном GeoJSON. Для привязки
фотографий необходимо отдельное представление временной геометрии:

```json
{
  "version": 1,
  "time_unit": "ms",
  "segments": [
    [
      [1784355272000, 87.1, 49.8, 2310]
    ]
  ]
}
```

Точка хранится как компактный массив `[utc_time_ms, lon, lat, ele]`; высота
может быть `null`. Точка без времени и невозрастающая временная метка разрывают
временной сегмент, чтобы не создавать ложную интерполяцию.

Рекомендуется хранить его отдельно от картографического GeoJSON, например в
one-to-one модели `TrackTimeline` с `JSONField`. Это не увеличивает ответы
обычной карты и не требует отдельной строки БД для каждой точки.

Нужно:

- заполнять timeline при загрузке и изменении GPX;
- пересчитать его для существующих треков идемпотентной командой
  `rebuild_track_timelines` после применения миграции схемы;
- сохранять границы сегментов;
- корректно учитывать точки без времени и большие разрывы;
- предоставить защищённый API отчёта с выбранными треками и timeline.

Критерий готовности: для фотографии с нормализованным UTC-временем сервис
находит соседние точки трека либо сообщает конкретную причину, почему привязка
невозможна.

Текущий серверный контракт: `TravelReport` хранит самостоятельный
упорядоченный набор выбранных треков через `ReportTrack`. Исходная группа нужна
для добавления новых треков, но её последующее изменение или удаление не
разрушает уже сделанный выбор. Авторизованный
`GET /api/reports/<report_id>/track-timelines/` возвращает только выбранные треки и
статус timeline: `ready`, `empty` (в GPX нет точек со временем) либо `missing`
(производные данные ещё не построены). До появления персональных API-токенов
эндпоинт использует серверную сессию.

## 2. Серверный каркас фотоподсистемы

Добавить отдельные Django-приложения или эквивалентные логические модули:

- `reports` — отчёты и выбранные треки;
- `photos` — пачки, фотографии, превью, состояния и аннотации.

Начальная предметная модель:

- `TravelReport`;
- `ReportTrack`;
- `PhotoBatch`;
- `PhotoAsset`;
- `PhotoPlacement`;
- `PhotoStack` и `PhotoStackMember`;
- `PhotoPreview`;
- `PhotoAnnotation`;
- `PhotoRendition`.

Минимальный API:

- получить доступные пользователю отчёты;
- создать пачку;
- массово зарегистрировать метаданные фотографий;
- назначить и вернуть восьмисимвольные `photo_key`;
- получить выбранные треки и их временную геометрию;
- обновить состояние пачки и фотографий;
- загрузить thumbnail/preview;
- прочитать и изменить основные метаданные фотографии.

Повтор запроса после сетевой ошибки не должен создавать вторую сущность.
Массовые операции получают клиентский идентификатор идемпотентности.

Для первой версии достаточно персонального API-токена, создаваемого в Центре и
сохраняемого LRPL через системное хранилище секретов. Полноценный OAuth можно
отложить.

Критерий готовности: тестовый клиент создаёт пачку из 20 фотографий, безопасно
повторяет тот же запрос и загружает одно preview.

## 3. Каркас LRPL

Разместить LRPL в том же репозитории, но оформить как отдельное устанавливаемое
приложение со своим entrypoint и зависимостями. Оно не должно импортировать
Django-модели Центра.

Предполагаемый стек:

- Python и локальный HTTP-сервер;
- HTML-шаблоны и обычный JavaScript без обязательной сборки;
- SQLite для локального индекса;
- Pillow для JPEG и растрового рендера;
- упакованный ExifTool для метаданных;
- Leaflet для карты;
- PyInstaller для дистрибутивов.

LRPL должен:

- слушать только `127.0.0.1`;
- открывать интерфейс в системном браузере;
- проверять `Host`/`Origin` и защищать изменяющие запросы;
- выполнять длительные операции в фоне;
- показывать прогресс сканирования;
- вести продуктовый и диагностический журналы с первого этапа.

Локальный индекс хранит:

- зарегистрированные корни и относительные пути;
- серверные UUID и `photo_key`;
- размер и время изменения файла;
- SHA-256 и визуальные отпечатки;
- извлечённый EXIF;
- очередь операций и состояние последней синхронизации.

Критерий готовности: локальное приложение выбирает отчёт, сканирует каталог и
показывает таблицу фотографий. На этом этапе нужно выполнить раннюю пробную
сборку PyInstaller хотя бы для основной ОС разработчика.

## 4. Импорт, калибровка и логические дни

Первый полезный вертикальный срез проходит путь:

```text
каталог
→ анализ EXIF
→ калибровка времени
→ подтверждение дней
→ синхронизация метаданных
```

### Экран калибровки

Показывать:

- группировку по камере;
- диапазон исходного времени;
- временную шкалу фотографий и треков;
- предлагаемые сдвиги;
- количество совпавших и непривязанных кадров;
- выбор трека;
- действие «игнорировать этот трек для пачки»;
- ручную поправку времени;
- карту для выборочной проверки результата.

Хранить отдельно:

- `captured_at_raw`;
- часовой пояс из EXIF, если он присутствует;
- `time_offset_seconds`;
- `captured_at_normalized`;
- источник и состояние подтверждения поправки.

### Экран дней

Показывать предложенные логические дни, число фотографий, диапазоны времени и
пограничные кадры. Поддержать массовое подтверждение и ручное исправление
отдельной фотографии.

Критерий готовности: реальная пачка проходит импорт, калибровку и деление по
дням без изменения EXIF.

## 5. Фильтрация похожих кадров

Реализовать локальный многоступенчатый поиск:

1. Сформировать широкие временные эпизоды по коротким разрывам между кадрами
   одной камеры.
2. Найти точные копии по SHA-256.
3. Внутри эпизодов применить difference hash, DCT perceptual hash и при
   необходимости более дорогое сравнение thumbnail.

Не сравнивать все фотографии со всеми. Сначала ограничивать кандидатов одной
пачкой, камерой, близким временем и совместимым соотношением сторон.

В интерфейсе временной эпизод является контейнером, а не одной стопкой дублей.
Он содержит вложенные визуальные стопки и одиночные кадры. Интерфейс позволяет:

- крупный рекомендуемый кадр;
- лента альтернатив;
- относительный индикатор резкости;
- просмотр увеличенного фрагмента;
- выбор одного или нескольких кадров;
- разделение стопки и действие «оставить все»;
- возврат к решению позднее.

Автоматического удаления нет. Ручные решения следует запоминать, чтобы
повторный анализ снова не склеивал отвергнутую пару.

После подтверждения метаданные всех кадров отправляются в Центр, а thumbnail и
preview — только для выбранных. Смена представителя приводит к загрузке его
изображений. Версия алгоритма и применённые пороги сохраняются.

Качество группировки важнее минимального времени расчёта. Фоновый анализ одной
пачки может занимать часы, если LRPL показывает прогресс, допускает безопасную
остановку и не пересчитывает уже сохранённые отпечатки без необходимости.

Критерий готовности: на реальном наборе пользователь заметно сокращает число
просматриваемых карточек, не теряя доступа к отклонённым кадрам.

После этого этапа достигается первая значимая пользовательская контрольная
точка: каталог из тысяч фотографий превращается в геопривязанный серверный
каталог отобранных кадров.

## 6. Метаданные и рабочие копии

Добавить независимые поля:

- место съёмки;
- подпись отчёта;
- короткий filename slug;
- изображённые объекты.

Реализовать:

- предложение slug по подписи;
- назначение позиции с шагом 10;
- предпросмотр канонического имени;
- создание каталога `work/` и рабочей копии;
- явное безопасное переименование;
- кнопку «Готово»;
- пересчёт хеша рабочей ревизии;
- генерацию и загрузку нового preview;
- обнаружение `changed-after-ready`.

Текущий RPL содержит административные регионы и GPX-waypoints, но не имеет
каталога вершин, ледников и рек. Первый срез географических имён должен работать
с waypoints, ручным вводом и общей моделью географического объекта. Источник
автоматических подсказок следует подключать через отдельный интерфейс провайдера,
не блокируя остальной MVP.

Критерий готовности: выбранная фотография получает стабильное имя, открывается
во внешнем редакторе, после обработки подтверждается и обновляется в Центре.

## 7. JSON-аннотации и композиция

Сначала зафиксировать общий JSON-контракт и покрыть тестами преобразование
координат:

- нормализованные координаты;
- связь с хешем рабочей ревизии;
- текст;
- прямая и ломаная стрелка;
- `z_index`;
- стилевые пресеты.

Затем реализовать два редактора одного формата:

- SVG поверх серверного preview в Центре;
- SVG поверх локального изображения в LRPL.

Минимальный UX:

- инструменты «Выбрать», «Текст» и «Стрелка»;
- перетаскивание элементов;
- добавление и удаление узла стрелки;
- светлый и тёмный стили;
- изменение порядка;
- undo/redo внутри сеанса;
- сохранение в Центр;
- предупреждение после изменения рабочей ревизии.

Локальный композитор создаёт новый файл, не перезаписывая рабочую копию:

```text
work/photo.jpg
+ annotations/photo-key.json
→ images/photo.jpg
```

Для первой реализации использовать Pillow и поставляемый вместе с LRPL шрифт с
кириллицей. Эталонные тесты должны проверять геометрию результата с допустимым
небольшим различием растеризации между ОС.

Критерий готовности: стрелка, созданная в Центре, занимает то же место в LRPL и
в полноразмерном финальном JPEG.

## 8. Упаковка и пилот

Собирать отдельные дистрибутивы для Windows, macOS и Linux. В комплект входят:

- Python runtime и LRPL;
- ExifTool;
- встроенный шрифт;
- статические ресурсы;
- миграции локальной SQLite.

Проверить:

- пути с кириллицей и пробелами;
- регистрозависимые и регистронезависимые файловые системы;
- длинные пути Windows;
- сетевые и синхронизируемые облачные каталоги;
- EXIF Orientation;
- аварийное завершение во время сканирования;
- повторный запуск и повтор операций;
- обновление LRPL без потери локального индекса;
- создание диагностического архива.

Пилот должен пройти как минимум на двух реальных путешествиях и нескольких
тысячах фотографий.

## Порядок первых коммитов

1. CLI-прототип EXIF, калибровки и похожих кадров.
2. Сохранение временных точек GPX и обработка существующих треков.
3. `TravelReport` и выбор треков.
4. `PhotoBatch`, `PhotoAsset` и минимальный API.
5. Каркас LRPL, SQLite и журналы.
6. Импорт каталога и массовая синхронизация метаданных.
7. Экран калибровки.
8. Подтверждение логических дней.
9. Стопки похожих кадров и оценка резкости.
10. Загрузка выбранных thumbnail/preview.
11. Метаданные и рабочие копии.
12. JSON-аннотации и локальный композитор.
13. CI-сборки для трёх ОС и пилот.

Каждый коммит должен включать относящиеся к изменению тесты. После появления
пользовательской функциональности необходимо синхронно обновлять раздел
`Возможности` в `README.md`.

## Не включать в первый вертикальный MVP

- редактор и генератор текста отчёта;
- Pandoc/LaTeX;
- передачу полноразмерных файлов через Центр;
- офлайн-синхронизацию;
- историю правок;
- RAW/HEIC;
- распознавание лиц, моргания и объектов в кадре;
- OpenRaster/XCF;
- произвольное рисование;
- автоматическую художественную раскладку подписей;
- сложную модель ухода часов камеры;
- двусторонний импорт проектов внешних редакторов.

SVG/OpenRaster можно добавить после стабилизации композитора: архитектура JSON
уже оставляет для них место.
