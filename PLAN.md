# RPL (Route Planner): план разработки

## Группы треков и архив исходных данных

Реализованная модель хранения разделяет неизменяемый `original_gpx_file` и рабочий
`gpx_file`. При загрузке создаются две копии; редактирование заменяет только рабочую.
Восстановление копирует архив в новый рабочий файл и пересчитывает производные данные.
Прежний рабочий файл удаляется после фиксации транзакции. Промежуточные версии не хранятся.

`TrackGroup` хранит название, описание, UUID, владельца и даты создания/изменения.
`TrackGroupMembership` связывает группу с треком и задаёт его позицию в группе.
Связь оформлена как many-to-many с явной таблицей участия. Сейчас отдельное ограничение
`one_group_per_track` разрешает только одну группу на трек; для нескольких групп
нужно снять его и расширить операции назначения и интерфейс выбора. Уникальность
пары группа/трек сохраняется. Позиции относятся к участию, не к самому треку.

Изменения состава и порядка проходят через транзакционные сервисы с блокировками.
Треки и группа принадлежат одному владельцу. Публичный просмотр соответствует
просмотру отдельных треков; управление доступно владельцу и суперпользователю.
Удаление группы удаляет только связи. Статистика группы вычисляется из текущих
данных треков; геометрия отдаётся как FeatureCollection без соединения маршрутов.

Разбиение по дням отложено: оно будет создавать самостоятельные треки, позволять
выбрать архив или текущий GPX и отдельно фиксировать происхождение частей.

Ниже сохранён исходный план разработки MVP; часть его этапов уже реализована.

## Назначение

RPL — сервис для хранения и отображения GPX-треков. В минимальной версии
администратор загружает GPX-файл, после чего трек доступен на отдельной странице
с картой OpenStreetMap и базовой статистикой.

В дальнейшем сервис должен поддерживать пользователей, загрузку треков из
обычного интерфейса и редактирование маршрутов на карте.

## Зафиксированные принципы

- Проект не использует Docker или Docker Compose.
- Приложение не привязывается к `systemd` или другому process manager.
- Локальная разработка ведётся в обычном Python virtualenv.
- Конфигурация окружения передаётся через переменные окружения и локальный
  `.env`, который не хранится в Git.
- PostgreSQL запускается как внешний системный сервис.
- Production предоставляет стандартные WSGI/ASGI entrypoints. Способ управления
  процессами выбирается отдельно при развёртывании и не влияет на приложение.
- На старте не создаём отдельное SPA и не добавляем обязательную JavaScript-сборку.
- Исходный GPX-файл сохраняется как мастер-копия данных.
- GPX-файлы получают случайные серверные имена; пользовательское имя файла не
  используется в storage path. Файлы распределяются по двум уровням каталогов
  из трёх hex-символов: `tracks/abc/def/<random>.gpx`.
- Python-код форматируется командой `ruff format` и проверяется командой
  `ruff check`; другие Python-форматтеры не используются.

## Технологический стек

### Backend

- Python 3.13.
- Django 5.2 LTS.
- PostgreSQL.
- `gpxpy` для чтения GPX.
- Django Admin для загрузки треков в MVP.
- `pytest` и `pytest-django` для тестов.
- Ruff как единый форматтер и линтер Python-кода.
- `pyproject.toml` для описания проекта и зависимостей.

SQLite может использоваться в изолированных тестах, но основная разработка
ориентируется на PostgreSQL. PostGIS на первом этапе не нужен. Его следует
подключать, когда появятся пространственный поиск, выбор треков внутри области и
другие серверные географические операции.

### Frontend

- Django Templates для серверного HTML.
- Bootstrap 5 для интерфейса и адаптивной вёрстки.
- Leaflet для карты.
- OpenStreetMap как исходная картографическая подложка.
- Небольшие ES-модули на обычном JavaScript для карты.

HTMX можно добавить позднее для фильтров, списков и форм с частичным обновлением
страницы. Для MVP он не является обязательной зависимостью. React, Vue, Alpine.js
и отдельный frontend build pipeline пока не нужны.

## Модель данных MVP

Основная сущность `Track` содержит:

- название;
- автоматически создаваемый случайный UUID для публичного URL;
- описание;
- исходный GPX-файл;
- дату загрузки;
- владельца (поле можно подготовить заранее, даже если работает один админ);
- дистанцию;
- набор и сброс высоты;
- минимальную и максимальную высоту;
- число точек;
- время начала, окончания и продолжительность, если они есть в GPX;
- границы трека;
- подготовленную геометрию GeoJSON в `JSONField`.

При загрузке сервер:

1. Проверяет размер, тип и корректность файла.
2. Безопасно разбирает XML/GPX.
3. Извлекает треки, сегменты, точки и доступные метаданные.
4. Рассчитывает статистику.
5. Преобразует геометрию в GeoJSON.
6. Сохраняет исходный GPX и результат обработки.

GeoJSON рассчитывается при импорте, а не при каждом открытии страницы. Исходный
GPX сохраняется, чтобы данные можно было обработать заново после изменения
алгоритмов.

## Интерфейс MVP

Планируемые маршруты:

- `/` — список треков;
- `/tracks/<uuid>/` — страница трека с картой и статистикой;
- `/tracks/<uuid>/geojson/` — GeoJSON трека;
- `/tracks/upload/` — загрузка GPX авторизованным пользователем;
- `/admin/` — административное управление треками и пользователями.

Страница трека должна:

- показывать подложку OpenStreetMap;
- отображать линию маршрута;
- обозначать начало и конец маршрута;
- автоматически выбирать масштаб по границам трека;
- показывать основную статистику;
- корректно работать на мобильных экранах.

GeoJSON отдаётся отдельным endpoint. Это уменьшает исходный HTML, позволяет
кэшировать геометрию и оставляет удобную точку интеграции для будущего редактора.

## Использование OpenStreetMap

- На карте всегда отображается атрибуция `© OpenStreetMap contributors`.
- URL тайлов и текст атрибуции задаются настройками, а не жёстко прошиваются в
  код компонента карты.
- Не реализуется фоновая или массовая загрузка тайлов.
- Для разработки и умеренной нагрузки допустим публичный tile server OSM.
- При росте нагрузки подложку можно переключить на другого провайдера или
  собственный tile server без изменения логики приложения.

## Этапы разработки

### 1. Каркас проекта

- Создать Django-проект и приложение `tracks`.
- Описать зависимости и поддерживаемую версию Python.
- Настроить PostgreSQL и конфигурацию через окружение.
- Добавить базовый Bootstrap-шаблон.
- Настроить static и media files.
- Настроить Ruff для форматирования и статической проверки, добавить тестовый
  каркас и документацию локального запуска.
- Добавить удобные команды через `Makefile`, не скрывая стандартные команды
  Django.

### 2. Модель и импорт GPX

- Создать модель `Track` и миграции.
- Реализовать сервис разбора GPX отдельно от views и моделей.
- Добавить проверку размера и содержимого файла.
- Рассчитывать статистику, границы и GeoJSON.
- Настроить Django Admin.
- Добавить тестовые GPX fixtures.
- Покрыть тестами корректные, повреждённые и граничные файлы, включая несколько
  треков и сегментов.

### 3. Просмотр треков

- Реализовать список треков.
- Реализовать страницу отдельного трека.
- Добавить GeoJSON endpoint.
- Подключить Leaflet и подложку OpenStreetMap.
- Отрисовать маршрут, начало и конец.
- Добавить автоматическое масштабирование и основную статистику.

### 4. Доведение MVP

- Добавить понятные сообщения об ошибках импорта.
- Проверить мобильную вёрстку и доступность интерфейса.
- Настроить HTTP-кэширование GeoJSON.
- Проверить поведение на больших, но допустимых GPX-файлах.
- Описать запуск через WSGI/ASGI без привязки к конкретному process manager.
- Подготовить минимальный checklist развёртывания без инфраструктурных шаблонов.

## После MVP

- Авторизация и принадлежность треков пользователям.
- Регистрация и управление профилем из пользовательского интерфейса.
- Поиск, фильтрация и сортировка.
- Высотный профиль с синхронизацией позиции на карте.
- PostGIS, административные регионы и пространственные запросы.
- Редактирование точек и сегментов на карте.

- Фоновые задачи для тяжёлой обработки, если в них появится необходимость.

## Географическая классификация

Для автоматической классификации треков планируется использовать административные
полигоны Overture Maps Divisions и PostGIS.

- Страны, регионы и районы хранятся как иерархические сущности `Region`.
- Геометрия региона хранится как `MultiPolygon` со spatial index.
- Связь трека с регионами хранит длину маршрута внутри региона и долю покрытия.
- Основным считается регион, содержащий наибольшую длину трека; дополнительные
  пересечённые регионы также сохраняются.
- GeoJSON остаётся подготовленным форматом для браузера, а пространственные
  вычисления выполняются по GIS-полям в PostgreSQL/PostGIS.

Импорт Overture не должен быть одноразовым скриптом. Нужна идемпотентная Django
management-команда для первоначальной загрузки и последующих обновлений данных.
Команда должна:

- принимать release/version Overture, страны, bounding box и административные
  уровни;
- поддерживать `--dry-run`;
- сохранять версию, источник и время импорта;
- загружать данные во временную staging-таблицу и проверять их до публикации;
- выполнять upsert по стабильному внешнему идентификатору;
- помечать исчезнувшие регионы неактивными, не разрывая существующие связи;
- атомарно переключать приложение на успешно проверенное обновление;
- пересчитывать классификацию только для треков, затронутых изменившейся
  геометрией;
- быть безопасной для повторного запуска после частичного сбоя;
- выводить статистику добавленных, изменённых, деактивированных и ошибочных
  объектов.

## Архитектурная граница

RPL начинается как server-rendered Django-приложение. Карта является отдельным
интерактивным компонентом, который получает подготовленный GeoJSON с backend.
Такой подход сохраняет простой и быстрый MVP, не мешая позднее развить карту в
полноценный редактор.
